▢composition & lifecycle

One graph, resolved on the first request.

The entire dependency graph is assembled in a single container call and resolved lazily; background tasks are lifespan-owned and drained inside the orchestrator's grace window; prod invariants fail closed at boot.

lifespan(app):
  RootConfig().validate_prod_invariants()
                          fail closed at boot
  build_container(channels=…)  one call · 7 providers
     AsyncContainer (APP scope, lazy)
                    resolves on 1st request
  start:  auth · alchemy · media  managers
                          own background tasks
  ── serve ──
  stop (finally · always reached):
     cancel + await every task
     → container.close()  dispose engines, aclose redis

  25s uvicorn drain  <  30s k8s grace
                 never SIGKILLed mid-flight

the one place dependencies are wired

build_container() registers 7 Dishka providers and hands back one AsyncContainer. Business code never constructs a collaborator: use cases and facades receive theirs by injection, and the only file that names a concrete implementation is a provider.py.

graceful drain

Each lifespan manager owns its background asyncio.Tasks -- the outbox relay, the stream consumers -- and cancels + joins every one on SIGTERM, even after one crashes. uvicorn's 25s drain sits inside a 30s k8s grace window, so in-flight work finishes before SIGKILL.

  • The graph is lazy. Nothing is instantiated at import; the APP-scope container resolves on the first HTTP request, so tests warm it explicitly and a boot never does hidden I/O.
  • Background tasks are lifespan-owned. The outbox relay and status consumer run as asyncio.Tasks a manager cancels and joins on shutdown -- no orphan survives the process.
  • Prod invariants fail closed. No admin token or CSRF secret under APP_ENV=prod and the app refuses to start; the worker refuses to start without its panel password.

◇configuration

Everything is an environment variable. Nothing reads one.

Config enters through typed Pydantic Settings and flows out through Dishka providers · no domain or app code ever touches os.environ. Two committed templates bound the surface: a minimal one that boots the stack, and the full annotated contract.

one prefix per context

MEDIA_ MEDIA_PROCESSING_ AUTH_ LOG_ METRICS_ POSTGRES_ VALKEY_ DB_EXAMPLE_LITESTAR_

Each context owns a config.py with a unique env_prefix, so two contexts can hold a TIMEOUT without collision and each settings class validates only its own slice of the environment.

the flow, one direction

env → Pydantic Settings → Dishka provider → constructor. Drift is a bug: every variable the code reads is present in the templates in the same change, and even per-worker mutable state -- the SSE FeedLimiter -- is a DI-provided singleton, never a module global.

  • The domain can't see the environment. Config is Pydantic Settings injected through Dishka; domain and app take plain constructor arguments and never touch os.environ -- verified across both layers, and the DI wiring makes it the only easy path.
  • Secrets are placeholders, never examples. Both templates ship empty secret slots with a generation hint -- the app validates their presence at startup, and .env itself is gitignored.

◇error model

One error taxonomy, one wire shape.

Every failure is named by the layer whose invariant broke, and the whole surface between exceptions and HTTP is a single dictionary that maps each class to an RFC 9457 problem-details response. Hover a class to trace it.

A 6-entry EXCEPTION_TO_PROBLEM map is the entire translation layer -- the four base classes plus two concrete framework cases (JwtDisabled, advanced-alchemy's NotFound). A new context error inherits its status and a stable urn:litestar-base:error:<slug> type for free -- no handler edits.

seen live e2e-tested

POST /videos/{id}/cancel on a terminal video raises InvalidTransition (a DomainError) that maps to 409 urn:…:invalid-transition; an unknown id maps to 404. test_cancel.py →

  • Every error has exactly one home layer. A four-class base taxonomy names which invariant broke; each context subclasses only its own layer, and the taxonomy is fully exercised -- no class exists without a raise-site.
  • Raw infrastructure exceptions are caged at the driven port. asyncpg / redis / OS errors are wrapped into PortError at a single kind of site -- translation lives in one file, not in scattered controller try/except.
  • 5xx bodies are hermetic. Full context is logged once at the boundary; a generic detail goes on the wire. Tracebacks and driver messages never cross, and truly-unexpected exceptions hit one prod catch-all that maps to 500.

▢observability on the layers

Bind the trace once. Each layer signs its own line.

One bind_contextvars(trace_id) in an ASGI middleware puts the id on every structured line of the request -- because merge_contextvars is the first processor, no lower layer re-threads it. Each layer adds its own layer tag; video_id carries correlation across the wire.

TraceIdMiddleware binds trace_idtransport
UploadVideoUC "video registered" video_id=Xapp
└─▶ video_uploaded stream ─▶
uploaded_consumer "received" video_id=Xadapters_driving
complete_job "processed" video_id=Xapp
◀─ video_status stream ◀─┘
status_consumer "applied" video_id=Xadapters_driving

processor chain

merge_contextvars → add_log_level → add_logger_name → TimeStamper(iso,utc) → StackInfoRenderer → CallsiteParameterAdder → dict_tracebacks → snitchbot → ProcessorFormatter -- the shared ProcessorFormatter renders one bounded JSON line to stdout and the JSONL file. No queue, no shipper, no second process.

the layer field explicit bind

Five Layer values (app, ports_driving, ports_driven, adapters_driving, adapters_driven) -- no DOMAIN, the domain never logs. App use cases bind it at the operation boundary; adapters hold a module logger. It is an explicit opt-in, not an auto-derived tag.

correlation

trace_id pins the chain to the originating HTTP request but does not cross the process boundary -- the SAQ worker is a separate process. video_id is logged at every stage and is identical on both sides of the streams, so one grep video_id=X follows the whole pipeline.

  • The domain and port interfaces log nothing -- no logger lives in any domain/ or app/interfaces/ file. Logging sits only where I/O and orchestration do.
  • One process writes, the UI tails. The admin viewer reverse-reads and tail -Fs the exact JSONL file, inode-aware through logrotate, streaming new rows over SSE with client-side filtering.
  • Metrics are multiprocess-safe. The master wipes stale shards and exports PROMETHEUS_MULTIPROC_DIR before forking; APP_WORKERS scales with no config change and module-level counters survive repeated app construction in tests.

▵test pyramid

The level is the directory.

Four levels, each a directory that mirrors src/; the level is auto-tagged by a path-reading collection hook, so -m unit selects a tier with zero hand-maintained markers. Hover a tier for its rule.

unit110 · domain · mocks forbidden
flow60 · app · every interface a fake
integration77 · one port+adapter · real infra
e2e93 · full app · no mocks

tests/<context>/<level>/

Grouped by bounded context first, then level -- the directory is the taxonomy. Integration and e2e run against real Postgres 18 and Valkey 8 via testcontainers, never a SQLite stand-in.

backend 340 worker 31 total 371

The tiers rank by isolation and speed, not head-count: a template earns trust by proving itself end-to-end, so e2e is deliberately heavy. Unit stays instant and mock-free; the pyramid is a rule about dependencies, not a quota.

  • Each level has a hard rule. Unit forbids unittest.mock entirely; flow requires every interface to be a fake or AsyncMock; integration and e2e forbid mocks and use real infra.
  • Rigor is legible from the path. No test hides its level -- the collection hook reads it from the directory, so a reviewer knows what a failure means before opening the file.

The same gate runs in four places.

One command -- ruff · mypy · lint-imports · pytest -- fired from pre-commit, GitHub CI, the Docker image, and the Taskfile, over both services. What passes locally is exactly what passes in CI.

architecture is machine-verified enforced

10 import-linter contracts guard bounded-context independence, an un-importable root shell, a dependency-free shared kernel, and strict inward layering. A cross-layer import fails the gate -- the hexagon on this page is a test, not a diagram.

One pinned toolchain, no drift: ruff and mypy are pinned identically in both services and run through local hooks, so the versions can never diverge from CI.

▵feature workflow

Every change walks the same path.

Docs at both ends, tests through the middle. This one is a convention, not a linter -- but it is written down, and the last step is machine-checked: the gate stays red until the docs match.

1
Frame the feature
Goal and boundary in a few lines -- which context owns it, what crosses the wire, what is out of scope.
2
Read the docs first
architecture.md, the owning context page, the relevant contract/ pages, any ADR that already constrains the area.
3
Write the design
A short spec: data flow, layer placement, changed wire shapes, error cases. New decision means a new ADR (≤40 lines).
4
Read the code
The owning context end-to-end plus the nearest analog (media_example is the reference) -- plan against what exists, not memory.
5
Implement inward-out
Domain first, then app, ports, adapters; tests at each level as you go -- unit → flow → integration → e2e.
6
Update every touched doc
Context page, contract on any wire change, ADR status, env templates for new vars. A stale doc is a bug.
